# T1 — lint rule validation against real data, 2026-09-13

Per spec 00 T1: verify the "2-3 already-instrumented real projects" premise, collect data via the
OTel Collector's file exporter (no `tracescope` code), then for each of the six candidate rules
(spec 03) answer by hand: would it fire, and would firing be useful.

## Step 1 — premise check

**Only the OTel demo app was available this session** (owner's explicit choice — "demo app only,"
not the ideal 2-3 independently-instrumented real projects). Reporting that plainly rather than
absorbing it, per spec 00's own instruction. One consequence, noted per-rule below: a
well-instrumented reference app is a poor test of rules 2 and 6, which are precisely about
*non-compliant* instrumentation — a clean project can only produce true negatives for those, not
confirm they're well-calibrated against a broken one.

## Step 2 — data collection, no tracescope code

`opentelemetry-demo` (official repo, `compose.yaml`, default load generator), OTel Collector's
`file` exporter added via the project's own designated customization seam
(`src/otel-collector/otelcol-config-extras.yml`), output at `/out/traces.jsonl`.

- **11,289 spans** across **2,226 traces**, **17 services**: ad, cart, checkout, currency, email,
  flagd, frontend, frontend-proxy, frontend-web, image-provider, load-generator, payment,
  product-catalog, quote, recommendation, shipping, telemetry-docs.
- Collected over ~1 minute of the demo's own synthetic load generator running unmodified.

## Step 3 — the six rules against this data

| # | Rule | Fired? | Verdict |
|---|---|---|---|
| 1 | High-cardinality span names | **No** — 87 distinct names, 11,289 total spans, ratio **0.77%** (predicate needs >50 distinct AND >30% ratio) | **Confirms STOP #6's flagged concern, measured, not hypothetical.** 87 > 50 easily, but the ratio is nowhere near 30% — distinct names grow sub-linearly (bounded operation vocabulary) while total spans grow with traffic, exactly as the spec's own written concern predicted. |
| 2 | Missing `service.name` | **No** — 0 / 11,289 | Expected on a well-instrumented reference app — this rule's value is on *broken* instrumentation, which this dataset can't exercise. Not evidence against the rule, just an untested case (see Step 1). |
| 3 | Broken context propagation | **Yes** — real orphans: product-catalog 19, cart 5, image-provider 4, frontend-proxy 2, currency 2, shipping 1, flagd 1; 1,632/2,226 traces have 2+ services | **Real, specific, actionable.** Fires on genuine cross-service parent-linkage gaps in a real app. |
| 4 | Attribute type conflict | **Yes** — `http.status_code` (int + string), `server.port` (int + string), `net.peer.port` (int + string), `http.request.body.size` (int + string), `http.response.body.size` (int + string) | **Real, specific, actionable.** Different SDKs across the demo's polyglot services (Go/JS/Python/Java/.NET) encode the same semantic attribute with different types — exactly the cross-SDK drift this rule exists to catch. |
| 5 | Long-duration leaf span (>1s, >50% of parent) | **Yes, 24 times — but all 24 are the same false-positive shape**: `flagd.evaluation.v1.Service/EventStream` (a long-lived gRPC **streaming** subscription), 3.0-3.3s each | **Would have been noise as specified.** A streaming/long-poll RPC is expected to run long — that's not a missing-instrumentation problem, it's the correct behavior of a subscription. The predicate as written can't distinguish "slow synchronous work" from "intentionally long-lived stream." |
| 6 | Deprecated semantic conventions (pinned table, HTTP semconv ~1.23+ stabilization) | **Yes — overwhelmingly: 12,025 of 11,289+ spans carry at least one deprecated key** (`http.status_code` 4,614; `http.method` 2,623; `http.url` 1,739; `http.target` 884; `http.scheme`/`http.flavor`/`net.host.name` 520 each; `net.host.port` 521; `net.peer.port` 81) | **Fires on nearly everything — this is the noise case T1's own decision table warns about.** The load-bearing finding: **the official OpenTelemetry demo app itself, today, is still instrumented with pre-1.23 HTTP semconv names.** If the ecosystem's own reference app hasn't migrated, this rule as specified would flag the large majority of real-world HTTP-instrumented services currently in production. Directly confirms the named concern ("false-positives on a project pinned to an older SDK") — not a hypothetical, observed. |

## Decision rule applied (spec 00's table, read per-rule since results diverge sharply)

- Rules 3, 4: "fires a handful of true, specific, actionable findings" → **the feature is real, proceed as specified.**
- Rule 1: "fires nothing" (as specified) despite 87 distinct names existing → **do not build the ratio predicate as written; report before proceeding** (done here).
- Rule 5: "fires on nearly everything within one class, and it's noise" → **tighten before shipping, do not ship as-is.**
- Rule 6: "fires on nearly everything" → **noise is worse than silence — do not ship as specified.**
- Rule 2: **inconclusive on this dataset alone** — needs a project with real instrumentation gaps to validate either way; recommend keeping it (ERROR tier, cheap, matches a real failure mode) rather than cutting on a null result.

## Recommendation — surviving rule set (evidence-backed, not the prior qualitative "six is probably three")

| # | Rule | Recommendation | Why |
|---|---|---|---|
| 1 | High-cardinality span names | **Keep, change predicate**: drop the ratio, use an absolute count with a bar clearly above this app's clean baseline of 87 (propose starting at **≥200 distinct span names**, cross-trace scope unchanged) | Ratio is measurably unreachable at scale (0.77% vs. a 30% bar); a clean 17-service polyglot app already produces 87 distinct names, so the bar must sit meaningfully above that. **Caveat: this dataset only gives a clean-baseline number, not a true-positive number** — the exact threshold still wants a genuinely bad project to calibrate against; 200 is a reasoned midpoint, not a measured optimum. |
| 2 | Missing `service.name` | **Keep as specified** | Untested-clean rather than disproven; cheap, ERROR-tier, catches a real and common first-instrumentation mistake that this demo app simply doesn't have. |
| 3 | Broken context propagation | **Keep as specified** | Validated with real, specific findings. |
| 4 | Attribute type conflict | **Keep as specified** | Validated with real, specific findings. |
| 5 | Long-duration leaf span | **Keep, narrow the predicate**: exclude spans whose `rpc.method`/name pattern indicates a streaming or long-poll call (e.g. gRPC server-streaming), or require the span to have no `rpc.*`/`messaging.*` attributes indicating an intentionally long-lived connection | As specified, it fires exclusively on a false-positive class in this dataset (100% of hits were the same streaming-RPC shape). Shipping as-is would train users to ignore the rule. |
| 6 | Deprecated semantic conventions | **Cut for v1**, or drastically narrow (exclude `http.method`, `http.status_code`, `http.url` — the three keys responsible for 8,976 of the 12,025 hits — and keep only genuinely rare/obscure deprecated keys) | Fires on ~100% of HTTP spans in a reference app maintained by the OTel project itself. As specified, this rule would be noise on the majority of real-world users' first run, which is the worst possible first impression for a linter. |

Net: **4 of 6 keep as-is or with a small predicate change (1, 2, 3, 4), 1 needs a real predicate fix
before shipping (5), 1 should be cut or narrowed to near-nothing (6).** This is sharper than the
prior "six rules is probably three" hunch — it says which three are solid, which one is close but
needs a fix, and identifies the actual mechanism (streaming RPCs; the ecosystem's own
non-migration) behind the two that need to change, rather than a general instinct.
