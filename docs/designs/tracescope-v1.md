## The strategic finding that reframed this review

The PRD's differentiator is "incumbents collapse on 10k-40k-span traces," evidenced by
jaeger-ui #645 / #562 / #186 and Grafana #114264. That evidence is real but it is about
*issues*, not current behavior. Jaeger's own release material describes a virtual viewport
handling traces up to 50,000 spans with testing reported at 80,000, while jaeger-ui #562
remains open. Both claims cannot be fully true and nobody has checked which describes
reality today.

Separately, the architecture pass established that a 40k-span trace is only 8-16 MB and
scanning it is microseconds in any language. The bottleneck is the render path and the
payload, not the store. Two consequences the PRD does not account for:

1. **"Virtualized waterfall" is table stakes, not a differentiator.** Jaeger may already
   have it. What remains of the technical edge is payload discipline (attributes fetched
   on click, columnar JSON) — real, but thinner than the PRD assumes.
2. **The performance thesis, if it holds, is won by browser-side work, not by Rust.** The
   credibility claim (stated priority 1) would rest on TypeScript and canvas, while Rust
   serves stated priority 3 (learning). See "Unresolved — needs the owner" below; this is
   the owner's call, not this document's.

Also live rather than hypothetical: otel-desktop-viewer shipped 0.5.0 in late August 2026
and was recently rebuilt on DuckDB. The "incumbents close the gap first" risk row is
present tense.

## Approach decision (0C-bis)

**CHOSEN: Approach A — verify before committing to the performance narrative.**

Alternatives considered: **B)** pivot the wedge to diagnostics now (3-4 weeks, no
performance race); **C)** build the full PRD as written (6-8 weeks); **D)** contribute
upstream instead (fix jaeger-ui #562, or add diffing to otel-desktop-viewer) — strong
credibility-per-hour and zero distribution problem, but no flagship artifact under the
author's control and nothing for the Rust-learning priority.

### What exactly is being verified

One hypothesis, stated precisely: **on a current version of each incumbent, opening and
interactively filtering a 40,000-span trace is slow enough that a well-built alternative
is visibly better to a developer.**

Not being verified here: market size, whether people want a local viewer (the OTel DevEx
survey already answers that), or whether Rust is faster than Go (irrelevant — the
bottleneck is the browser).

### Spike schedule and method

**Day 1-2, before any product code.** This is the first work item, ahead of M0.

**Step 0, early exit.** Jaeger's own release material claims a virtual viewport handling
50k spans with testing at 80k. Try to reproduce *their* claim first, before building any
harness. If a current Jaeger v2 opens an 80k-span trace smoothly, the performance thesis is
falsified on day 1 by the incumbent's own benchmark and the rest of the spike is
unnecessary — go straight to the THESIS DEAD row. Cheapest possible kill shot, so it runs
first.

- Subjects: Jaeger v2 all-in-one and otel-desktop-viewer 0.5.0. **Record exact versions and
  test dates** — otel-desktop-viewer shipped 0.5.0 two weeks ago and is actively developed,
  so a 0.6 could land mid-spike. Re-check both before publishing anything.
- Inputs: synthetic traces at 10k / 40k / 100k spans, plus the OpenTelemetry demo app
  under load as a real-telemetry control.
- Measured, in a real browser via `performance.now()`, not backend-only: time from
  trace-open click to interactive first paint; latency per filter/search keystroke;
  peak browser memory. Ten runs (not five), report median and p90, warm cache, one machine,
  machine specs published, and **report the spread** — if run-to-run variance exceeds 30%
  the measurement is not usable for a threshold decision and needs a better harness before
  the gate can be called.
- Fairness disclosure, stated in the write-up rather than hidden: Jaeger all-in-one is a
  collector plus storage plus UI, not a single local binary. The comparison is of the
  *developer-visible experience*, which is the honest framing and the one that survives
  scrutiny. Do not claim a like-for-like architectural benchmark.
- Deliverable either way: a public benchmark repo (generator + harness + raw numbers) and
  a write-up. This is a credibility artifact independent of the outcome.

### Pre-registered decision rule (commit to this BEFORE seeing numbers)

Deciding the threshold after seeing data means rationalizing whatever comes back.

**Where the numbers come from.** Rev1's thresholds were invented, which is a real defect:
undefined thresholds let any result be rationalized into any row. These are derived from two
things instead.

*Perceptual boundaries* (Nielsen / Card, long-standing and uncontroversial): ~100ms reads as
instantaneous; ~1s preserves flow of thought; beyond ~10s attention is lost. A keystroke
filter therefore has to be under roughly 100ms to feel live, and a trace open has to be
around or under 1s to not break flow.

*A relative gap requirement.* The question is not "is the incumbent slow in absolute terms"
but "would a developer notice the difference." A sub-2x improvement inside the same
perceptual band is not a differentiator anyone can feel, let alone one that survives an HN
comment section. So a claim needs **both** a ≥2x gap **and** a crossed perceptual boundary.

| Spike result at 40k spans | Verdict | Action |
|---|---|---|
| Incumbent crosses a perceptual boundary badly: **>2s to open** (flow broken) or **>300ms per keystroke** (not live), or fails to load — and our designed baseline can plausibly land ≥2x better on the same box | **THESIS HOLDS** | Performance leads the launch; publish the benchmark post as the headline. Fund the extra render-path tuning. |
| Incumbent already sits inside the good bands: opens **<1.2s** and filters **<120ms** | **THESIS DEAD** | Performance is not a story. Launch on diagnostics + linter. Publish the benchmark anyway, honestly: "the incumbents are fine now, here is what is still broken." |
| Anything between, **or any result whose spread straddles a boundary** | **INCONCLUSIVE** | Treat as thesis-dead for positioning. Diagnostics and linter lead; performance becomes a supporting claim, not a headline; no perf-headline post. |

Straddling counts as inconclusive deliberately: with real measurement variance, the honest
move on an ambiguous number is the conservative branch, not the flattering one.

**What is and is not thesis-independent.** Being precise, because rev1 waved at this.

*The product is the same in every branch.* Approach B was never a different architecture —
it is the same OTLP ingest, the same trace-partitioned store, the same waterfall, the same
linter, minus the extra render-path tuning and minus the benchmark-as-headline. The store
design was chosen because it is *simpler* than the DataFusion alternative it replaced, so no
branch of that table triggers a rewrite or discards work.

*What actually changes across branches:* the launch narrative, whether the perf-headline
post ships, and whether the extra tuning hours (canvas renderer, packed binary payload) are
funded. That is the honest scope of the gate. It is smaller than "whether to build," and the
decision table above should be read that way.

## Vision

### 10x Check

Every tool in this category is **passive** — Jaeger, Tempo, Aspire, otel-desktop-viewer,
otel-tui. They are windows you stare through; you bring the questions. The 10x version is
**active**: it tells you what you did not ask.

The tool already sees every span the service emits, and after the architecture pass it
already computes most of what a linter needs — orphan counts, span-name cardinality,
missing `service.name`, attribute types. Today that sits in a debug panel as counters.
Turned into sentences it becomes a linter for telemetry: a compiler that type-checks
instrumentation. Nobody in the category does this.

### Platonic Ideal

You add OTel to a service for the first time. You run one command. The terminal says
*receiving from `checkout` on :4318*. You hit your endpoint. The trace prints as a tree,
inline. Under it: three warnings about your instrumentation. You fix them, re-run, and it
says `✓ clean — 340ms, -2 spans vs last run`.

You never opened a browser. When you do, it is because you have a 40k-span agent loop and
you want the waterfall — and it opens instantly.

Positioning consequences: terminal-first-with-a-browser is unoccupied (otel-tui is
terminal-only, everyone else browser-only), and a tool already in the terminal loop is
trivially also in CI (`tracescope assert --no-orphans --no-n-plus-one`) — a capability
that does not exist anywhere today.

**Why the linter survives a dead thesis.** It is a claim about telemetry *correctness*,
which is orthogonal to render *speed*. "Jaeger renders 40k spans fine" does not make "your
instrumentation emits 1,203 distinct span names and nobody tells you" any less true. The
two features answer different questions, so disproving one does not touch the other.

**Effort honesty on the linter.** The rule *inputs* are free — the `ORPHAN` flag, the
per-trace name interner, `MISSING_SERVICE_NAME`, and the flat attribute triple-store all
already exist in the design. The rule engine, thresholds, message wording, and tests are
not free, which is why the estimate is 1-1.5 weeks human rather than the 1 week claimed in
rev1.

**Export demand caveat.** Grafana #61377 (export trace as JSON to ease sharing during
troubleshooting) and the existence of `ddexport` show demand for getting traces *out of* a
tool. They are adjacent evidence, not direct evidence that this product's users want this
export. Treated as a cheap bet on a plausible need, not a validated requirement.

## Linter rule definitions (thresholds, so they are not re-litigated at implementation)

Session-scoped unless stated. All thresholds configurable; these are the defaults.

1. **High-cardinality span names** — fires when distinct span names > 50 **and** distinct >
   30% of total spans. Reports the top 5 offenders with example names.
2. **Missing `service.name`** — any span whose resource lacks it. Reports count and percent;
   names the endpoint and protocol it arrived on.
3. **Broken context propagation** — orphan spans grouped by (child service, unresolved
   parent span id). Fires when a service has >0 orphans whose parent was never seen inside
   the retention window **and** the trace contains spans from 2+ services. Per-trace.
4. **Attribute type conflict** — same attribute key observed with 2+ different value types
   in one session. Reports the key, both types, and counts.
5. **Long-duration leaf span** — zero children, duration > 1s, **and** > 50% of its
   parent's duration. Suggests missing instrumentation inside it.
6. **Deprecated semantic conventions** — attribute key matches a deprecation table pinned
   to a stated OTel semconv version (pin the version in the repo; bump deliberately). Note
   the maintenance cost: this table needs updating as OTel evolves.

### Where linter findings surface (decided 2026-09-13)

Terminal summary **plus** a dedicated UI tab, with three severity tiers.

- **Terminal:** on startup and then throttled (every ~5s when findings change), a compact
  block — counts by severity, top 3 findings, and a pointer to
  `localhost:PORT/instrumentation`. This is a summary block, deliberately *not* the full
  terminal tree renderer, which stays deferred.
- **UI:** its own tab, separate from the Receiver panel. The Receiver answers "is data
  arriving"; the linter answers "is the data any good." Different questions, different tabs.
- **Severity:** ERROR for things that break analysis (broken propagation, missing
  `service.name`); WARN for things that cost money or degrade downstream (high cardinality,
  attribute type conflicts); INFO for advisory (long leaf spans, deprecated semconv).
  Without tiers, six simultaneous findings read as flat noise and none get fixed.

### Validating that the rules are worth shipping

Thresholds above are reasoned, not measured, and six rules may or may not be enough to
carry the product's repositioning. Cheap test, run once the rule engine exists and before
the linter is claimed as the headline: point it at the OpenTelemetry demo app and two or
three real instrumented projects, and count what fires.

- Fires nothing on real code → the rules are too conservative or the premise is wrong.
  Either way, do not build a launch narrative on it.
- Fires on nearly everything → thresholds need tightening, or findings need better ranking
  before they are useful rather than noisy.
- Fires a handful of true, specific, actionable findings per project → the feature is real.

This is a few hours and it is the difference between "the linter is the headline" as a claim
and as a fact.

## Diagrams

> Diagrams 2, 4 and 5 were redrawn after the Outside Voice pass. The accumulator versions

**1. System architecture** — see Section 1 above (ingest → mpsc → writer → store, with lint
and export as new *read-side* consumers; neither touches the ingest path).

**2. Lint data flow (on request — nothing on the ingest path)**
```
span accepted ──▶ mpsc ──▶ writer ──▶ RwLock<Store>      (evictable)
                                            │
      `lint` / GET /api/lint ──▶ store::LintView (read lock, copy out)
                                            │
                                    rules.rs: one pass over resident traces
                                            │
                                    Vec<lint::Finding>{rule, count, examined,
                                                        samples: [(trace_id, span_idx); ≤3]}
                                            │
                          ┌─────────────────┴─────────────────┐
                    terminal formatter                  api/rest → Lint tab

`lint <file.otlp>` ──▶ ingest::convert (Stage 2 load path) ──▶ same rules.rs
```
No accumulator, no cap, no epoch, no reset: the input is whatever is resident at the moment
you ask, and the finding says how many traces that was.

**3. Export pipeline**
```
GET/CLI export <id> ─▶ snapshot trace ─▶ secret scan ─▶ warn(keys,counts)
                                             │
                        serialize JSON (escape <) ─▶ inline into viewer HTML
                                             │
                              size check ─▶ ExportTooLarge? ─▶ refuse
                                             │
                              temp file ─▶ rename ─▶ path printed
```

**4. Lint request outcomes** (replaces the accumulator state machine — no state, no states)
```
lint ──▶ store empty?  ──yes──▶ "no data yet"        (NOT "0 issues found")
           │
           no ──▶ run rules over N resident traces
                    │
                    ├── findings ──▶ ≤6 rows, each: count + "examined N traces" + ≤3 samples
                    └── none     ──▶ "clean across N traces"
```
The fix-and-verify loop: fix the instrumentation, restart the app, run `lint`, read clean.
Reaching clean costs a restart and needs no reset command.

**5. Module dependency**
```
main ─▶ ingest{grpc,http,convert} ─▶ store{trace,writer,LintView}
  │                                        ▲     ▲     ▲
  ├─▶ lint{rules,finding,terminal} ────────┘     │     │
  ├─▶ api{rest,sse} ─────────────────────────────┘     │
  ├─▶ export{mod,redact} ──────────────────────────────┘
  └─▶ demo
```
`lint` depends on `store`, never the reverse, and `ingest` does not know `lint` exists.
`lint/accumulator.rs` is not a module in this design.

**6. Distribution / rollout**
```
tag ─▶ CI: macOS arm64 + Linux x86_64 ─▶ single static-ish binary ─▶ GitHub Release
                                              │
                          rollback = user pins an older tag

```

## Outside Voice pass (Claude subagent; Codex not installed) — 6/10, three findings taken

The reviewer's two strongest hits landed on **my own Finding 1**, which was half wrong:

1. **"Never pruned" breaks the fix-and-verify loop.** The platonic ideal is "you fix them,
   re-run, it says clean". A monotonic accumulator can never reach clean without killing the
   viewer. Finding 1 fixed a silent-reset bug and created an unreachable success state.
2. **"The cap doubles as the detector" does not survive arithmetic.** The cap is a memory
   guard sized in thousands; rule 1 fires in the dozens, so the cap never participates. Worse,
   once the name set saturates, distinct-names stops growing while total spans keeps growing,
   so any ratio-based rule *decays below its threshold* — the detector goes quiet at maximum
   badness. That claim was stated confidently and was wrong.

| # | Finding | Decision |
|---|---|---|
| 6 | Monotonic-forever makes "clean" unreachable; saturation silences the ratio | ~~Monotonic within an **explicit epoch** — `lint reset` + a UI button, every finding labeled `since <time>`. Cap becomes a **latch**: on saturation rule 1 fires unconditionally and renders `≥ cap`~~ **SUPERSEDED: on-request lint has no epoch to reset and no cap to saturate. The critique was right and this fix was the wrong shape.** |
| 7 | Three span sources (live, `--demo`, loaded file) silently share one accumulator | ~~**Scope per source.** Demo feeds its own scope and the generator emits deliberately imperfect instrumentation; a loaded file is linted on demand, labeled by filename~~ **SUPERSEDED: no shared state to scope. Every `lint` names its input — resident traces, or the file path. Demo ships as `examples/checkout.otlp`, not as a live source.** |
| 8 | Export had no size stance and no filtering stance | **View-only, no filter box** (keeps the "Decided Against" entry closed). **No span cap** (owner decision) — instead a post-serialization size warning naming GitHub's 25 MB attachment limit. Subtree export deferred to TODOS |

Also taken as direct corrections, no question needed:

- **Evidence links must be generation-aware.** The PRD's own `RESURRECTED` flag means an
  evicted-then-recreated trace is resident again with fresh indices `0..n`, so a stored
  `span_idx` navigates to a *different span* silently. Fix: per-trace generation counter,
  compared at link time; mismatch renders the sample as plain text.
- **The six summary rows are not homogeneous.** *(Also mooted — all rules now read the same
  input, the resident traces, at the same instant.)* Rules reading the epoch accumulator and rules
  computed per-resident-trace mean different things; each row states its scope.
- **The secret-scan warning goes to stderr, the written path to stdout**, so a developer
  piping the path still sees the warning (advisor).
- **`<` is serialized as `<` in JSON, not HTML-escaped** — the distinction matters, and
  conflating them lands an implementer in the double-escaping bug option B described.

### Left standing, for the owner

- **"Six rules is probably three."** The reviewer argues rule 2 duplicates the Receiver panel
  and rule 6 (semconv deprecation) is a rotting table that false-positives on pinned older
  SDKs. Plausible and not decided here — it is a rule-by-rule call best made while writing them.
- **Validate the rules before building the engine.** The CEO plan schedules rule validation
  *after* the rules exist. Inverting it is nearly free: dump attribute keys and span names from
  the OTel demo app plus 2–3 real projects and check by hand whether each proposed rule would
  fire and whether the firing is useful. An afternoon, before ~1.5 weeks of engine work.
- **The reviewer's "No" on accepting three expansions with an unverified thesis.** Recorded,
  not acted on: the owner accepted them explicitly against a documented HOLD SCOPE
  recommendation. The sequencing point above is the version of that objection worth acting on.

  the one that normally fails on dark; adjust the token, never the rule.
- **Tabular numerals** on every duration and count column, or the waterfall's numbers jitter.
- Theme the browser surfaces from these tokens: selection, caret, scrollbars, focus ring,
  underline offset. Leaving them at browser defaults is the cheapest tell that nothing was
  designed.
- More space above a heading than below it. One radius value. No shadows in v1 — there is no
  depth in this UI, so a shadow would be decoration.

## Keyboard and accessibility

| Key | Action |
|---|---|
| ↑ / ↓ | move the focused row; the virtualized list keeps it mounted and in view |
| ← / → | collapse / expand the focused subtree |
| Enter | open span detail for the focused row |
| `/` | focus the filter box |
| Escape | clear the filter, then close the detail panel |

Semantics: waterfall is `role="tree"` with `aria-level` and `aria-expanded` per row and
`aria-rowcount` for the virtualized total. Visible focus ring on every interactive element,
drawn from `--link`. Touch targets ≥44px in the exported file's narrow layout. Lint findings
are a list of headings, so a screen reader hears the tier, then the finding, then the count.

## NOT in scope (design)

- **A responsive live UI.** Desktop-only, stated. It binds to localhost; nobody browses it
  from a phone. The export carries the narrow layout instead.
- **A light/dark toggle.** System preference only — no control, no stored state.
- **A full DESIGN.md.** The ~15 tokens above are the whole system for v1.
- **Vim keybindings and a `?` shortcut sheet.** Arrows cover the interaction; aliases are a
  surface to document and keep consistent forever.
- **A disabled filter box in exports.** The provenance bar states that filtering is
  unavailable; a dead control would say it twice.
- **Animation.** No entrance motion, no transitions beyond the row highlight on new spans.
  There is no narrative on this surface for motion to serve.
- **Per-language SDK snippets in the empty state.** Two env vars cover the common case; four
  SDK snippets are four things to keep correct in a tool that claims to need no configuration.

No DESIGN.md, no components, no CSS. What the plan already settles and this review builds on

template (so tokens land in one place), T9's `DataSource` seam means the exported file runs the
